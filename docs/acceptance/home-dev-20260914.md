## RWO result: PASS

Claim and PV (created for this gate and intentionally retained):

```text
PVC rwo-gate  Bound  pvc-6f33f660-5529-4096-9450-1f2394a51a9c  ReadWriteOnce
PV  pvc-6f33f660-5529-4096-9450-1f2394a51a9c  Bound  longhorn-nfs-gateway-acceptance/rwo-gate
```

The controller reported `LonghornNFSExport/rwo-gate` as `Ready`, with PVC,
protocol, helper, endpoint, and cleanup Conditions satisfied. The helper used
`Recreate`, mounted the RWO Longhorn PVC, and exposed TCP NFSv3 on 2049 plus
mountd on 20048.

Because a ClusterIP is not directly reachable from the macOS LAN, the test
used a local port-forward for both TCP ports and mounted through it:

```sh
kubectl -n longhorn-nfs-gateway-acceptance \
  port-forward svc/rwo-gate-nfs 2049:2049 20048:20048
sudo -n mount_nfs -3 -o tcp,resvport,port=2049,mountport=20048 \
  127.0.0.1:/export /tmp/longhorn-nfs-rwo-mac
```

Verified:

1. macOS wrote `mac-marker.txt`; the same file was readable through the mount.
2. Unmount and remount succeeded, with the marker still readable.
3. The helper Pod was deleted and recreated by the Deployment; restarting the
   port-forward and reconnecting from macOS succeeded, including a new write.
4. Deleting only the `LonghornNFSExport` removed the Deployment, Service,
   ConfigMap, NetworkPolicy, and helper Pod. The PVC and PV remained Bound.

## RWX result: BLOCKED / FAIL (independent compatibility gate)

Claim and PV (created for this gate and intentionally retained):

```text
PVC rwx-gate  Bound  pvc-5d32fb43-db8e-4eb2-a1b6-aff7ec5c7306  ReadWriteMany
PV  pvc-5d32fb43-db8e-4eb2-a1b6-aff7ec5c7306  Bound  longhorn-nfs-gateway-acceptance/rwx-gate
```

The controller reported `LonghornNFSExport/rwx-gate` as `Ready`, and the
helper Pod itself became Ready. The Longhorn CSI mount was confirmed as an
NFSv4.1 mount inside the helper:

```text
10.43.172.249:/pvc-5d32fb43-db8e-4eb2-a1b6-aff7ec5c7306 /export nfs4 ...
```

A second Pod mounting the same RWX claim wrote `from-share-manager.txt`; the
Ganesha helper read the same file. This confirms the Longhorn share-manager
NFSv4 side of the path.

The macOS NFSv3 mount through Ganesha failed with `Permission denied` (exit 13).
Ganesha logged that its VFS FSAL could not resolve/export the NFSv4-mounted
`/export` filesystem (`resolve_posix_filesystem(/export) returned No such file
or directory` and no usable export entry). Therefore the NFSv4-to-NFSv3 bridge
is not accepted. This remains an independent locking, identity, caching, and
re-export compatibility blocker; RWX Longhorn support must not be advertised.

The RWX export and writer Pod were then removed by name. The RWX PVC and PV
remain Bound; no PVC or PV was deleted or modified by cleanup.

## Follow-up blockers

- Fix or replace the RWX re-export path (likely a Ganesha FSAL/re-export or
  architecture change) and repeat the independent macOS gate.
- Decide whether native macOS clients should receive a reachable NodePort or
  LoadBalancer endpoint rather than requiring a port-forward; the current
  acceptance intentionally used a port-forward because generated Services are
  ClusterIP.
- Keep the RWO result scoped to this disposable home-dev cluster and pinned
  images; it is not yet a Macgrubernetes production release gate.
